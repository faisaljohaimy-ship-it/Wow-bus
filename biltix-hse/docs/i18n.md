# BILTIX Risk AI — translation guide (Arabic RTL / English LTR)

Owner: A-SHELL (`js/core/i18n.js`, `js/i18n/core.js`). Binding API: `docs/specs/v3-precision/CONTRACT.md` §4.
English (LTR) is the default interface language since v3.7.1 (a saved Arabic choice needs `settings.langChosen`, set by
any language change). Arabic is the primary product-copy language (RTL); English is a complete experience, not a
fallback. Every user-visible string, `aria-label`, `title`, placeholder, toast, chart label, validation
message and export header goes through the runtime below.

## 1. The runtime in one minute

```js
import { i18n, t, tn, L } from '../core/i18n.js';

t('cockpit.metrics.open');                       // "Open risks" / "المخاطر المفتوحة"
t('core.common.updated', { time: fmt.relative(iso) });  // '{time}' interpolation
tn('core.activity.count', 12);                   // plural form + {count} formatted by fmt.num (numerals-aware)
i18n.label('taskStatus', task.status);           // stored enum value → display label
L(risk, 'title', 'aiRisks');                     // data text in the active language
i18n.localize(risk, 'aiRisks');                  // the whole record, merged with its English mirror
i18n.term(task.owner);                           // people, organisations, authorities, roles, places
i18n.lang(); i18n.dir(); i18n.locale();          // 'en' · 'ltr' · 'en-GB'
await i18n.setLang('en');                        // persists, sets <html lang dir>, emits bus 'lang:change'
```

Views receive the same helpers in `ctx` (`ctx.i18n, ctx.t, ctx.tn, ctx.L, ctx.status, ctx.motion`).
`t()` never throws: missing in the active language → Arabic value → the key itself. Lookups that fell
back are collected in `i18n.missing()` as `'<lang>:<key>'` strings (diagnostics only; nothing is
written to the console).

Switching language: the shell (`js/app.js`) re-renders its chrome (rail, tab bar, filters, palette,
banner, activity panel, data chip, toasts, document title) and the router re-mounts the current view
with the same params and scroll position. **Views must not cache translated strings at module level**
— build them inside `render()`. Module-level dictionaries are fine; translated *values* are not.

## 2. Dictionary files and key naming

One namespace per module, one file per namespace: `js/i18n/<ns>.js`

```js
// js/i18n/cockpit.js
export default {
  ar: { heading: { title: 'قمرة قيادة المخاطر' }, metrics: { open: 'المخاطر المفتوحة' } },
  en: { heading: { title: 'Risk cockpit' },        metrics: { open: 'Open risks' } },
};
// js/views/cockpit.js
import dict from '../i18n/cockpit.js';
i18n.register('cockpit', dict);           // at import time; registering again merges
```

- Keys are `ns.path.to.key`, lower camelCase segments: `cockpit.metrics.open`, `settings.weights.sumError`.
- Group by screen area, not by word: `cockpit.register.empty.title`, not `cockpit.noRisks`.
- The same English word in two places with two meanings gets two keys.
- Arabic values are the product copy (moved from the code, corrected only when wrong). English is
  natural, professional product English — not a word-for-word rendering. Sentence case for labels
  and headings ("Mitigation tasks", not "Mitigation Tasks").
- Placeholders are `{name}`; pass already-formatted values (`fmt.num`, `fmt.date`, `fmt.currency`),
  because `t()` inserts params as plain strings (years and codes must not get grouping separators).
- Never build sentences by concatenating fragments (`t('a') + ' ' + n + ' ' + t('b')`): word order
  differs between Arabic and English. Use one key with placeholders.
- Registered namespaces today: `core` and `status` (shell, `js/i18n/core.js`), `ui`, `charts`,
  `radar` (A-UI), `enum` (A-DATA-EN, `js/i18n/enums.js`), plus one per view (`cockpit`, `airisks`, …).

The shell namespace `core` holds: `core.app.*` (product name, tagline), `core.nav.<viewId>.title|short`
for all 22 views (rail title, two lines allowed / tab-bar short title) and `core.nav.groups.*`,
`core.shell.*`, `core.lang.*`, `core.filters.*`, `core.data.*` (data chip + popover),
`core.activity.*` (activity panel, feed types), `core.alerts.*`, `core.cmdk.*`, `core.score.*`,
`core.rating.*`, `core.router.*`, `core.errors.*` and `core.common.*` (common words: save, cancel,
close, retry, simulated, illustrative values, to be agreed …). Reuse `core.common.*` before adding a
new generic word to a view namespace.

## 3. Plurals

A plural value is an object with CLDR categories; `tn(key, count, params)` picks the form with
`Intl.PluralRules(lang)` and fills `{count}` with `fmt.num(count)`:

```js
ar: { count: { zero: 'لا أحداث', one: 'حدث واحد', two: 'حدثان', few: '{count} أحداث', many: '{count} حدثاً', other: '{count} حدث' } },
en: { count: { zero: 'No events', one: '{count} event', other: '{count} events' } },
```

- Arabic needs all six forms: `zero` (0), `one` (1), `two` (2), `few` (3–10), `many` (11–99),
  `other` (100, 1000 …). Arabic `one`/`two` usually omit the digit ("حدث واحد", "حدثان").
- English needs `one` and `other`; `zero` is optional and is used for 0 in both languages when present.
- Missing category → `other` → the first form given.
- `t()` on a plural object uses `params.count` when it is a number, otherwise `other`.

## 4. Data dictionaries (seed content in English)

Stored data stays Arabic (no migration). English lives in mirrors, keyed by record id:

```js
// js/i18n/data/<file>.js  (owner A-DATA-EN) — merged by js/i18n/data/index.js
export default {
  aiRisks: { 'AIR-1': { title: 'Ambiguous clause …', recommendation: { action: 'Request …' } } },
  terms:   { 'م. سارة القحطاني': 'Eng. Sarah Al-Qahtani' },
};
```

- `L(record, field, ns)`: English → the original value **deep-merged** with
  `mirror[ns][key][field]` (strings replace; objects merge key-wise; arrays merge index-wise and keep the
  original length; `{}` / `null` / missing = no change); else `record[field + 'En']` (runtime records
  from the engines carry `titleEn`, `detailEn`, `descriptionEn` …); else `terms[value]`; else the
  original. Arabic → the original.
- Mirror key: `record.id`, else `record.code` (currencies), else `'_'` (singletons: company, product,
  roadmap). Pass an explicit 4th argument when a collection is keyed otherwise:
  `L(template, 'text', 'feedTemplates', index)`.
- Namespaces are the collection names listed in CONTRACT §4 (sites, risks, incidents, permits,
  inspections, courses, workers, isoClauses, legalRegister, integrations, sensors, company, projects,
  contracts, suppliers, commodities, boqItems, scheduleTasks, resources, approvals, subcontractors,
  costLines, changeOrders, currencies, labourIndex, aiRisks, tasks, alerts, pipelines,
  validationSources, validationRules, quarantine, connectors, auditLog, roadmap).
- Loading: `js/core/i18n.js` imports `js/i18n/data/index.js` (listed in `DATA_DICTIONARY_FILES`) on the
  first switch to English, or at boot when the session starts in English; `setLang('en')` resolves only
  after the data is registered, so the view never renders half-translated. Hovering or focusing the
  "EN" button warms the import. Arabic sessions do not need these files. Add a new data file to
  `js/i18n/data/index.js` (or to `DATA_DICTIONARY_FILES`) — a path that does not exist would show as a
  404 in the console.
- Enum values: never mirror them; display with `i18n.label(enumNs, value)`. `js/i18n/enums.js` exports
  `{ ar: { enum: { <enumNs>: { <storedValue>: label } } }, en: { enum: { … } } }` and is registered as
  namespace `enum` by the shell at boot. `label()` looks the value up directly (stored values may contain
  dots, e.g. `'الغبار PM2.5'`) and falls back to the Arabic label, then to the value itself (English
  stored ids such as `red` read better untranslated than as an Arabic label).

## 5. Formatting (never hand-format numbers or dates)

`fmt` follows `i18n.locale()` (`ar-SA` / `en-GB`) and, independently, the numerals setting
(`latn` / `arab` → `-u-nu-…`). Language and numerals are separate settings: English with Arabic-Indic
digits and Arabic with Western digits are both valid.

| Need | Use | Arabic (latn) | English |
|---|---|---|---|
| Integer / decimal | `fmt.num(n, { maximumFractionDigits })` | 12,345.6 | 12,345.6 |
| Compact | `fmt.compact(n)` | 12.5 مليون | 12.5m |
| Riyal | `fmt.currency(n)` · `fmt.currency(n, { compact: true })` | ‏12,500,000 ر.س.‏ | SAR 12,500,000 · SAR 12.5m |
| Percent | `fmt.pct(87)` · `fmt.signedPct(-2)` | 87% · −2% | 87% · −2% |
| Delta | `fmt.signed(3)` | +3 | +3 |
| Date | `fmt.date(iso, { style })` | 10 نوفمبر 2026 | 10 November 2026 |
| Date + time | `fmt.dateTime(iso)` | 10 نوفمبر 2026، 09:00 | 10 November 2026, 09:00 |
| Hijri | `fmt.hijri(date)` | 30 جمادى الأولى 1448 هـ | 30 Jumada I 1448 AH |
| Relative | `fmt.relative(iso)` | قبل 3 دقائق | 3 minutes ago |
| Duration | `fmt.duration(ms)` · `{ style: 'long' }` | 5 س 12 د · 5 ساعات و12 دقيقة | 5h 12m · 5 hours 12 minutes |
| Weekday | `fmt.dayName(iso)` | الثلاثاء | Tuesday |

`fmt.digits(text)` converts ASCII digits inside free text to the active numeral system.

**Time zone.** Every instant (a timestamp with a time) is shown in `Asia/Riyadh` (`fmt.timeZone`), the
sites' zone and the app-bar clock's, whatever the viewer's browser zone. Calendar days (`'2026-11-10'`,
or a `Date` at local midnight passed to `fmt.date` / `fmt.dayName`) are shown as that day with no zone
conversion. `fmt.dateTime` always treats its input as an instant. Pass `{ instant: true }` to
`fmt.date` when a local-midnight `Date` is really a moment in time. `tests/fmt-tz.test.mjs` checks this
under UTC, UTC+14, Los Angeles and Riyadh.

Known limit: "today" and overdue checks in the selectors use the browser's local day. For a viewer
outside UTC+3 they can differ from the Riyadh day for up to a few hours around midnight.

## 6. Bidi rules for codes, numbers and mixed text

- Codes (`AIR-1042`, `CT-2026-014`, `PTW-5521`, ISO clause `6.1.2`) are Latin and never break:
  render them in `<span class="code mono" dir="ltr" translate="no">` (the shell's `richText()` does it
  for free text; views use the same pattern). Never translate or localise the digits of a code.
- A number next to a unit stays one bidi run: `fmt.num(v)` + `' '` + unit, unit translated
  (`i18n.label('unit', u)`), and the pair wrapped in an element with `dir="auto"` when it sits inside
  text of the other direction.
- Signed values come from `fmt.signed` / `fmt.signedPct` (U+2212 minus; Intl's bidi marks are kept
  so the sign stays on the right side of the digits in RTL).
- English names inside Arabic sentences (Primavera P6, Autodesk APS, Oracle ERP) need no markup;
  if a sentence *starts* with a Latin word in Arabic UI, wrap the sentence in `dir="auto"` or keep
  the paragraph `dir` from the document.
- Direction-dependent icons (chevrons, "next", arrows) mirror in LTR; status glyphs never mirror.
- CSS uses logical properties only (`margin-inline-start`, `inset-inline-end`, `text-align: start`);
  JS reads `i18n.dir()` or `document.documentElement.dir` at call time, never at import.
- Charts: categorical axes follow the reading direction; time axes always run left → right.

## 7. Language selection, persistence and the first frame

Order on load: `?lang=ar|en` (query string or the hash query, e.g. `/?lang=en#/cockpit` or
`#/cockpit?lang=en`) → `settings.lang` (saved in `localStorage['biltix-hse:v1'].settings.lang`) →
Arabic. The pre-paint script in `index.html` applies the same rule to `<html lang dir>`, sets the
theme / numerals / background / density / motion attributes and preloads the 400 weight of the active
language's font (`plex-arabic-arabic-400.woff2` or `plex-sans-latin-400.woff2`), so the first frame is
already in the right direction and typeface. It also sets `html[data-calendar]` from `settings.calendar`
(`gregorian` | `hijri` | `both`, default `both`); `css/base.css` uses it to hide the app-bar clock line
that will stay unused (`.clock-hijri` for `gregorian`, `.clock-date` for `hijri`), so only the lines
boot will fill reserve space. `js/app.js` `applySettings()` keeps the attribute in step when the setting
changes. The URL parameter is applied, persisted and removed from
the address bar (a later switch is not overridden on reload). The switch "ع | EN" is in the app bar
(and in the "More" sheet on phones); its options carry `lang="ar"` / `lang="en"` and name each
language in itself.

## 8. Adding a language (e.g. Urdu)

1. `js/core/i18n.js`: add the code to `LANGS`, its direction to `DIRS` and its locale to `LOCALES`.
2. Every dictionary: add a `<code>: { … }` side (missing keys fall back to Arabic — keep `i18n.missing()`
   empty before shipping). Plurals: check the CLDR categories of the language.
3. Data: add mirrors for the new language (today the data loader is English-only: generalise
   `DATA_DICTIONARY_FILES` per language) and `<field><Code>` fields from the engines.
4. `js/core/fmt.js`: add the language's duration words / letters, fallback month and weekday names,
   compact and currency fallbacks, Hijri era label.
5. `index.html` pre-paint script + `js/app.js` language switch: accept the code and preload its font
   (A-STYLE adds the woff2 subset and `@font-face`).
6. Run the checks in §9 for the new language.

## 9. Testing Arabic and English

- Switch from the console: `await window.biltix.i18n.setLang('en')`; inspect `window.biltix.i18n.missing()`.
- QA harness: `node scratchpad/qa/qa.mjs --routes <ids> --lang ar,en --theme dark,light --viewport 1440x900,1024x768,390x844 --clock 2026-11-10T09:00:00+03:00 --out <dir>`
  (`--lang en` opens `/?lang=en#/<route>`).
- Arabic-text probe (English mode): walk the text nodes and the `aria-label` / `title` / `placeholder`
  attributes of the page, skip elements inside `[lang="ar"]` (the language option "ع" / "العربية"),
  count characters in U+0600–U+06FF. The shell (everything outside `<main>`) must be at 0; for `<main>`
  list every leftover with its source record (a data string not yet in the dictionaries).
- Numerals probe (Arabic mode, numerals = latn): Western digits everywhere; with numerals = arab no
  ASCII digit outside codes.
- Check `<html lang>` / `dir`, the document title, a language switch on a scrolled page (position
  kept), back / forward after a switch, and a reload (language persisted).
- Node: `node -e "import('./js/core/i18n.js').then(async ({ i18n }) => { await i18n.setLang('en'); … })"`
  — the runtime and `fmt` have no DOM dependency.
